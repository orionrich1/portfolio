# 포트폴리오 프로젝트 — Cursor 하네스 운영 가이드

> **목적**: AI(Cursor)에게 일을 시키는 방법과, 역할별 금지 사항을 한곳에서 확인한다.  
> **하네스 수정 권한**: 테스터 + Owner 전용. 다른 역할은 수정 요청 시 거절한다.

---

## 프로젝트와 기술 스택 (이 저장소)

- **이름**: 이윤식 포트폴리오(단일 페이지 웹사이트)
- **구성**: `src/index.html`(본문) · 루트 `index.js`(스크롤·모달·GSAP 등) · `src/index.css`(Tailwind 진입) · `img/` 등 정적 자산
- **빌드·개발**: Node.js · **Parcel** (`npm run dev` — 기본 포트 5000) · `npm run build`로 배포용 산출물 생성
- **스타일**: Tailwind(문서 내 CDN + 빌드 파이프라인의 `tailwind.config.js`) · 다크 배경 + 라임 악센트(구현 기준은 `DESIGN.md`)

CodeMoa 등 **다른 저장소**에서 쓰던 Spring·Gradle 표현은 **이 문서·명세의 예시로만** 두지 않는다. 이 저장소 기준은 위와 같다.

---

## 전체 구조 (규칙 파일)

```
항상 적용 (공용)
├── 00-global-direction.mdc
├── 05-technical-patterns.mdc   ← 공통 패턴(해당 시)
└── (있으면) .cursorrules

역할 하네스 (활성 1개만 — 나머지는 「폐기」)
├── 01-planner-harness.mdc
├── 02-developer-harness.mdc    ← 역할 미지정 시 기본
├── 03-designer-harness.mdc
└── 04-tester-harness.mdc
```

**적용 규칙**: 추론·행동에는 **`공용` + `활성 역할 하네스 1개`**만 쓴다. 비활성 `01`~`04`는 인용하지 않는다.  
상세 표는 `.cursor/rules/00-global-direction.mdc`의 **역할 시스템**을 본다.

---

## 워크플로 (요약)

```
1. 기획자  →  docs/PRODUCT_SPEC.md 만 갱신 (섹션·백로그)
2. 개발자  →  PRODUCT_SPEC.md · QA_SCRATCH.md 반영해 구현
3. 디자이너 →  동일 명세의 화면·토큰에 맞춰 UI 정리
4. 테스터  →  명세·하네스 준수 검토; 미통과만 docs/QA_SCRATCH.md → 통과 시 비움
```

---

## AI에게 일 시키기 (역할별)

### 기획자

```
기획자로서 [섹션명]에 맞게 PRODUCT_SPEC.md를 갱신해줘.
```

**출력**: `docs/PRODUCT_SPEC.md`의 해당 `##` 섹션(또는 백로그). **별도 `*-spec.md` 생성 금지.**

### 개발자

```
개발자로서 @docs/PRODUCT_SPEC.md 의 [섹션] 수락 조건을 구현해줘.
```

**출력물**: 주로 `src/index.html`, `index.js`, `src/index.css`, `tailwind.config.js`, `package.json` 등 이 저장소 루트 규칙에 맞는 파일.

**완료 시**: 로컬에서 `npm run dev`(또는 이미 떠 있으면 HMR) 후 **브라우저 새로고침**으로 확인 가능하게 하고, 확인 URL(예: `http://localhost:5000/#projects`)을 완료 메시지에 적는다.

### 디자이너

```
디자이너로서 @docs/DESIGN.md 와 PRODUCT_SPEC의 [화면/섹션]을 맞춰줘.
```

**출력물**: 동일하게 HTML/CSS·Tailwind 클래스·애니메이션 톤 정리. 백엔드 코드는 없다.

### 테스터

```
테스터로서 [섹션명]이 PRODUCT_SPEC 수락 조건을 만족하는지 검토해줘.
```

**출력물**: 미해결만 `docs/QA_SCRATCH.md`. **통과 시 파일 본문 비우기 또는 삭제.** 주제별 `*-quality.md` 신규 생성 금지.

**주의**: 「빌드만」「테스트 실행만」으로는 소스 수정 권한이 생기지 않는다. 테스터는 **실행·로그·스크린 기준 보고**까지만 하고, 수정은 **개발자로서** 전환 시 개발자 영역이다.

---

## 금지 요약 (역할별)

| 역할 | 하지 말 것 (요지) |
|------|-------------------|
| 기획자 | 코드 작성, 하네스 무단 수정 |
| 개발자 | 기획서 임의 축소, 하네스 무단 수정 |
| 디자이너 | 비 UI 영역(예: 배포 스크립트) 임의 변경, 하네스 무단 수정 |
| 테스터 | 앱 소스·빌드 스크립트 직접 수정(보고만), 승인 없는 하네스 수정 |

세부 Must NOT은 각 `.cursor/rules/0x-*.mdc`를 따르되, **이 저장소**는 Java·Gradle이 없으므로 그에 해당하는 조항은 **적용 대상이 아니다.**

---

## 하네스 수정 (테스터 + Owner)

1. 테스터가 개선안 제안 → Owner 승인 → `.cursor/rules/*.mdc` 또는 `.cursorrules` 수정  
2. 변경 사항을 팀(또는 Owner)에게 공유

---

## `docs/` 파일 역할

| 파일 | 역할 |
|------|------|
| `HARNESS_GUIDE.md` | 본 가이드(운영·역할) |
| `DESIGN.md` | 시각·토큰·타이포(단일 참고) |
| `PRODUCT_SPEC.md` | **기능·섹션·수락 조건·백로그 단일 원본** |
| `QA_SCRATCH.md` | 테스터 임시 이슈(통과 시 비움) |
| `site-renewal-full-test-report.md` | 점검·수동 테스트 **기록용**(명세 원본 아님) |

명세와 스크래치를 **한 파일에 섞지 않는다.** 미착수 과제는 `PRODUCT_SPEC.md` 백로그로만 옮긴다.

---

## 기획서 수명 (찌꺼기 방지)

구현·검증이 끝나면 `PRODUCT_SPEC.md`의 해당 수락 조건을 `[x]`로 맞추거나, 미착수는 **백로그 표**로만 남긴다. 상세는 기획자·개발자·테스터 하네스의 「기획서 수명 주기」를 본다.

---

## 자주 묻는 질문

**역할을 안 주면?**  
→ 기본은 **개발자 하네스(`02`)**가 활성이다.

**기획서 없이 고쳐 달라고 해도 되나?**  
→ 재작업을 줄이려면 `PRODUCT_SPEC.md`에 먼저 반영하는 편이 좋다.

**하네스가 현실과 안 맞아요.**  
→ 테스터에게 개선안을 올리고, Owner 승인 후 `.mdc`를 수정한다.
